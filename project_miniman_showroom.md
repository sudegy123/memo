A separate, isolated copy of [[project-miniman-shop-fan]]'s working folder (`Documents/miniman showroom`, copied from `Documents/miniman revamp`) built at the user's request to turn the site into a "3D interactive viewing room" — camera-driven navigation between zones instead of page loads, kept as its own copy so the live 2D site (`miniman revamp`) stays untouched.

**Architecture:** `showroom.html` is a single-page shell. `assets/3d/scene.js` builds a procedural room (perimeter wall, ceiling light panels, glowing backdrop panels, pedestals) and loads the real Air Jordan 1 × Dior GLB (see [[reference-mazin-3d-web-lessons]] for GLB lessons that also applied here) as the Home centerpiece. `assets/3d/camera-rig.js` is a state machine that flies the camera between zones along a Catmull-Rom path (never a cut). `assets/3d/router.js` is hash-based (`#shop`, `#about`, `#contact`) since this is a static-file site with no server rewrites — still gives real deep-linking + back/forward. `assets/3d/showroom.js` is the orchestrator wiring scene+rig+router+DOM zone overlays+a performance guard (drops DPR/shadows once if fps < 32). `assets/3d/shop-holo.js` builds a ring of holographic, interactive product cards (real catalog data + photos) orbiting the Shop pedestal — hover pauses the ring and lifts the card, click navigates to `product.html?slug=...`.

**Hologram displays:** each zone pedestal (Shop/About/Contact) got a procedural "hologram" — canvas-drawn line-art icon (bag/info/chat) floating in a glowing beam with a rising scan ring — built via `hologram()` in scene.js. Shop's was replaced by the interactive product-card ring once that was built (the static icon would just clutter it).

**Real bugs found and fixed this session (all confirmed via Playwright, not assumed):**
1. Idle mouse-parallax used `camera.rotation.y += sway.x*0.02` INSIDE the per-frame loop — a `+=` every frame is cumulative, so even a still mouse caused a slow runaway spin. Fixed by recomputing an absolute look-at offset from the rig's own target each frame (never accumulates). Verified: two screenshots 4s apart with zero mouse movement are now pixel-identical.
2. Zone HTML content (`.sr-zone__inner`) had no height cap — on a short viewport (e.g. 1010×610) content taller than the available space overflowed UPWARD past the viewport top (behind the nav, unreadable) since nothing allowed it to scroll. Fixed with `max-height:100%; overflow-y:auto` on the inner box.
3. An accent column (pure decoration) sat almost dead-center in BOTH the Shop and Contact camera sightlines simultaneously (their view directions overlap) — cut straight through the "FRESH ON THE SHELF" heading. Fixed by dropping that one column rather than chasing a position that dodges two views at once.
4. **The big one — holographic card hover/click didn't work at all despite correct raycasting code.** Root cause, found by testing at TWO levels: (a) `.sr-zone.is-active` was `position:fixed;inset:0;pointer-events:auto` — a full-viewport invisible box sitting above the WebGL canvas (z-index 10 vs 0) at EVERY pixel, swallowing all events before they reached the canvas, even over empty space with nothing visibly there. Fixed by moving `pointer-events:auto` down to only `.sr-zone__inner` (the actual bounded content box). (b) Even after that fix, `<main class="sr-zones">` (the zones' shared parent, `position:relative;z-index:10;height:100dvh`) was STILL intercepting events — because `pointer-events:none` on a child does nothing if the ANCESTOR itself is the element occupying that hit-test box. `pointer-events` is inherited, so setting `pointer-events:none` on `.sr-zones` and re-enabling only on `.sr-zone__inner` fixed it at the root.

**How the last bug was actually diagnosed (reusable method):** `document.elementFromPoint(x,y)` in a Playwright `page.evaluate()` — walked the ancestor chain at the exact coordinates a real click was landing on, and it named the blocking element directly (`H2` inside `.sr-zone__inner--wide`, then later `MAIN.sr-zones`) instead of guessing from CSS. Also used `mesh.getWorldPosition(new mesh.position.constructor())` (not `mesh.position` directly, which is LOCAL and wrong for `.project(camera)`) to compute exact expected screen coordinates for a rotating 3D object, rather than eyeballing pixel positions off a screenshot (which drifts as soon as the object keeps animating). A synthetic `canvas.dispatchEvent(new PointerEvent(...))` at those exact coordinates isolated "is the app logic correct" from "is the real OS-level pointer-events chain reaching the canvas at all" — it worked when real `page.mouse.move()` didn't, which is what pointed at a DOM-layering bug instead of a raycasting bug.

**Sandbox testing caveat:** this scene (room + GLB + hologram ring) is heavy enough that swiftshader (software GL) reported 0 fps in this sandbox during some tests — real per-frame state (mesh positions/rotation) can go stale between test steps if you assume normal frame timing. Always re-derive exact expected coordinates fresh via `page.evaluate()` immediately before interacting, never reuse coordinates read from an earlier screenshot.

**Desktop-only for now** — user explicitly deferred mobile (touch gestures, `SECTIONS_MOBILE` camera rig is stubbed in code but untested) until their weekly credits refresh. Not yet done: sculpted Blender room (current room is procedural primitives), LOD tiers, cross-browser/real-GPU testing.

**Full-catalog Shop wall (later sub-task):** user rejected the original "3 auto-rotating cards" Shop hologram — wanted the WHOLE catalog browsable in 3D, not a teaser. Rebuilt `shop-holo.js`'s `buildProductHologram()` to arrange ALL products (not `.featured().slice(0,6)`) into tiered rings (`PER_RING = 7` cards per ring, extra products stack as additional rings centered on the pedestal height) instead of one flat ring. Added `setFilter(categorySlugOrNull)` (hides/shrinks non-matching cards via `targetScale`) and `nudge(deltaRad, t)` (manual spin + resets the auto-idle-rotate timer) as new exports. `showroom.html`'s module script now: passes `Catalog.products()` (full list) to the builder; renders category pills from `Catalog.categories()` into `[data-sr-category-pills]`, wiring clicks to `holo.setFilter()`; and replaced the old plain `click` listener with pointerdown/pointermove/pointerup drag-vs-tap logic (`moved < 6px` on pointerup = tap → navigate to `product.html?slug=...`, otherwise it was a drag → `holo.nudge()` was already called during pointermove, no navigation). Pill styling added to `showroom.css` (`.sr-shop__pills`).

**Major pivot — showroom became the WHOLE site, not a preview of it:** user clarified the Shop/About/Contact zones weren't supposed to be teasers that link out to the old flat pages (`shop.html`/`product.html`/`about.html`/`contact.html`) — they wanted the entire storefront (product detail, cart, checkout, full About/Contact) to happen inside the 3D showroom itself. Built a full-viewport overlay panel system (`#sr-overlay`, `assets/3d/panels.js`, `window.SRPanels`) that slides in over the 3D canvas and never navigates away:
- **Product panel** reuses the REAL `product.html` markup + `product.js` almost unchanged — just added a guard (`document.body.hasAttribute("data-sr-showroom")`) so its auto-init (which reads `?slug=` from the URL and would otherwise stomp the panel with "not found") is skipped, and exposed `window.Wing.ProductView = { render, notFound }` so `panels.js` can call it directly with an explicit product object. Related/recently-viewed product links inside the panel are intercepted (`a[href*="product.html?slug="]`) and re-render in place instead of navigating.
- **Cart panel** is a NEW lightweight renderer in `panels.js` (not a reuse of `cart.js`'s page controller, which only self-inits once at page load against whatever's in the DOM at that instant — wrong lifecycle for a reopenable panel). Drives entirely off the existing `window.Wing.Cart` data API; re-renders on the `wing:cart` event. `Cart.open` is monkey-patched to `panels.js`'s `openCart` after `cart.js` loads (the real cart.js never defined `.open()` — `product.js`'s "add to cart" button already called `Cart.open()` expecting this).
- **Checkout is intentionally simplified**, not a port of `checkout.js`: the real checkout is Supabase-account-gated (email must already be a registered customer) which is a big auth dependency out of scope for this pass. Instead it's a WhatsApp-order panel — same pattern the product page's existing "Order via WhatsApp" button already used, extended to the whole cart (itemized message + total, opens `wa.me` with a prefilled message, clears the cart). Flagged this simplification to the user rather than silently downscoping it.
- **About/Contact panels** are hand-authored condensed content (not verbatim copies of the full multi-section marketing pages) — a full landing page's scroll-reveal/parallax sections don't fit a modal overlay, and `main.js`'s reveal/counter logic only wires up `.reveal`/`[data-count]` elements once at initial page load anyway (wrong lifecycle again for injected-later content), so those classes were deliberately left off the panel markup. Contact panel keeps the real info cards + form, with its own inline mailto submit handler (`main.js`'s `[data-form]` binding also only runs once at load and wouldn't see this form).
- Nav gained a cart icon with a live item-count badge (`[data-sr-cart]` / `[data-sr-cart-count]`).
- Shop zone's "Full shop page" escape-hatch link was removed entirely (the wall already IS the full catalog); About/Contact zone CTAs now open their panel instead of navigating to the flat page.

**Verification status:** confirmed via Playwright — full catalog loads (10/10 products, 5 pills incl. "All"), category filter correctly hides non-matching cards (e.g. filtering to "Running" left 1 visible mesh), drag-to-rotate correctly spins the ring (`group.rotation.y` changed by the expected amount for the drag distance). Hover-to-cursor-pointer and the click handler's internal logic (`downProduct` correctly picked as the raycasted product, `moved` correctly stayed 0 on a still tap) were BOTH confirmed correct via temporary debug logging — but the actual `location.href` navigation never completed within an 8s `waitForURL` in this sandbox, because the perf guard logged the scene running at 1fps (swiftshader software rendering + the full 10-card wall pushed the already-heavy base scene, see the existing sandbox caveat above, past its breaking point) — a single-threaded renderer that busy with synchronous rAF draw calls can starve the navigation commit even though the JS-level click logic already fired correctly. This is almost certainly a sandbox-only artifact, not a real bug, but it was NOT independently confirmed on a real GPU — flag this to the user and suggest a quick real-browser click-to-product-page check before calling the full-catalog wall fully done. (Superseded in practice: clicking a card now opens the in-showroom product panel via `window.SRPanels.openProduct()` instead of a `location.href` page navigation, which sidesteps this specific stall — confirmed working via Playwright by calling `SRPanels.openProduct()` directly, though the real drag/raycast pointer path to trigger it wasn't re-tested with the panel system.)

**5th "Miniman" overview zone (new):** user wanted a wide establishing shot of the whole room BEFORE Home — added as the new default landing zone (no-hash URL), pushing Home/Shop/About/Contact to be entered from it. Implementation: `showroom.js` SECTIONS/SECTIONS_MOBILE gained a `miniman` key (`pos:[0,5.2,11], look:[0,0.6,-1.5], fov:46` desktop — pulled back and elevated well beyond any other zone's camera position to frame the full room), `router.js`'s default/no-hash key changed from `"home"` to `"miniman"` (both places it was hardcoded), and a new `#sr-miniman` zone section (nav-button "Miniman", first in both the nav bar and `<main class="sr-zones">`) with "Step inside" (→ home) and "Go straight to the Shop" CTAs. Home's own zone heading was demoted from `<h1>` to `<h2>` since Miniman is now the page's true top-level heading. No changes needed to `camera-rig.js` (its Catmull-Rom travel logic is fully generic over whatever `sections` dict it's given) or to the goTo()/showZone() zone-toggle logic in `showroom.js` (also generic, driven by `[data-sr-zone]`/`[data-sr-nav]` DOM attributes).

Verified via Playwright: lands on miniman by default (camera at the new pulled-back position), and miniman→home→miniman→shop navigation all correctly update both the active zone and the URL hash. One testing note: the wide 46°-FOV establishing shot renders far more of the heavy scene at once, which pushed real-world travel completion well past the ~1.1s animation duration in this sandbox's slow software rendering (a `waitForTimeout(1500)` was too short; `waitForFunction` polling was needed) — a sandbox rendering-speed artifact per the existing caveat below, not a routing bug.

**Sandbox network caveat:** this workspace apparently has no real internet/DNS access — `config.js`'s Supabase project URL fails to resolve (`ERR_NAME_NOT_RESOLVED`), so any `api.*` call (store config, coupons, totals) hangs for ~15s before its `.catch()` falls back to defaults. This made the cart panel's "Checkout" button (which only renders after `Cart.totals()` resolves) appear to hang in testing — it's not a code bug, just this sandbox lacking network access; on a real connection (or with Playwright given actual internet) this should be near-instant.
