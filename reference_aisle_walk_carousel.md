## Concept
Scroll or vertical drag walks a virtual camera down a corridor. Products are placed in alternating rows on the left/right "walls," each row given a fixed Z-depth (`-(i+1)*GAP`). As the user scrolls, a single `depth` value eases toward a `targetDepth`, and every row's on-screen Z is `row.z + depth` — so scrolling forward makes deeper rows approach the camera.

## Core mechanics
- `.stage{perspective:700px}` + `.track{transform-style:preserve-3d}` — one perspective context, rows nested inside as 3D children.
- Each row: `translate3d(side*SIDE, -50%, z) rotateY(-side*22deg) scale(scale)`, where `side` alternates -1/+1 to put items on left/right walls, and `rotateY` angles the card to face the walkway (like shop windows along a hallway) rather than facing straight at the camera.
- `scale = max(.4, 1 - abs(z)/3000)` and `fade = max(0, 1 - abs(z+300)/2200)` — distance-based scale/opacity falloff, plus a visibility cutoff (`z > 500 || z < -6000`) so far-off rows aren't transformed every frame for nothing.
- Navigation: `wheel` event accumulates into `targetDepth` (clamped to `[0, (N+1)*GAP]`), plus vertical pointer-drag as an alternative for touch/trackpad users.
- `depth` eases toward `targetDepth` via exponential smoothing each `requestAnimationFrame`, not a CSS transition — keeps drag and wheel input feeling consistent (same pattern as the coverflow/spotlight carousels).

## Gotcha
- `GAP` (the z-distance between rows) and `SIDE` (x-offset from center) are the two knobs that control how "tight" vs "spacious" the aisle feels — a small `GAP` makes rows overlap awkwardly as they pass camera; too large and scrolling through 8 products takes forever. 620px/260px worked well for 8 items at a 700px perspective.
- Only one `perspective` context is used here (on `.stage`) — see [[reference_product_browsing_paradigms]]'s nested-perspective bug note for why stacking `perspective` on two ancestors in the same chain compounds multiplicatively and blows up scale.

## Upgrade pass (v2) — richer visuals, momentum nav, layout variety, per-product inspect
Requested as a follow-up polish round covering four axes at once:
1. **Richer visuals** — per-product ambient `.glow` (radial-gradient blur behind the card, tinted with the product's own `tone`), a floor `.refl` reflection (mirrored SVG art, `scaleY(-1)` + a `mask-image` gradient fading it out), and a `.fog` overlay (`linear-gradient`/`radial-gradient` near the vanishing point) plus per-row `filter:brightness()/saturate()` falloff with distance so far rows genuinely recede into haze instead of just fading opacity.
2. **Better navigation** — drag now carries real velocity into inertia on release (`vel` tracked from pointer delta/time, applied as `targetDepth += vel*18` on pointerup), and after ~220ms of no input (`scheduleSnap`, debounced via `setTimeout`) the camera snaps to the nearest product's `stopDepth` rather than resting at an arbitrary point mid-aisle. A vertical dot rail (`.progress`) on the right shows position and is independently clickable to jump straight to any product.
3. **Layout variety** — per-row jitter seeded from a deterministic `rnd(i * constant)` hash (not `Math.random()`, so the layout is stable across reloads): varied row spacing (`gapJit`), varied distance-from-path (`sideJit`), a small extra `rotJit` on top of the base wall-facing rotation, and a `scaleJit` size variance — replaces the original perfectly-uniform alternating grid.
4. **Per-product inspect mode** — clicking a card (guarded by a `wasDrag` flag so a drag-to-navigate gesture never misfires as a click) freezes camera movement, pulls that one card to dead-center via a fixed transform, dims/blurs every other row, and shows a name/category/price panel with a close pill + Escape-key + backdrop-click to resume.

### Bugs hit building the inspect mode (both fixed, both worth remembering)
- **Off-center "centered" element**: `.row` is positioned `left:50%;top:50%` with **no `translateX(-50%)`** baked in — the original code got away with this because the aisle's `side*SIDE` offset (±260px) dominated and masked a ~110px rightward bias. The moment a transform tried to place a row at true dead-center (`x=0`, inspect mode), the bias became obviously visible (card rendered off to the right). Fix: any transform meant to visually center a `.row` must explicitly include `translateX(-110px)` (half the 220px card width) — don't assume `left:50%` alone centers an absolutely-positioned box with an off-origin transform.
- **Stray oversized transform**: initial inspect transform (`translateZ(320px) scale(1.25)`) combined with the 700px stage perspective compounded to an oversized, partly-clipped card — same family of "did the perspective math actually check out" mistake as the dolly-zoom bug in [[reference_product_browsing_paradigms]]. Tuned down to `translateZ(260px) scale(1.15)`, verified the rendered box actually fits the viewport via a Playwright screenshot rather than assuming the numbers were fine.
- Also worth remembering as pure UI hygiene: a `<div class="close">` pill button will silently stretch to 100% width unless given `display:inline-block` — block-level buttons inside a `text-align:center` panel don't self-size to content.

**Testing method**: verified with a scripted Playwright pass (idle → scroll into the aisle → find the one currently-visible-in-viewport row via `getComputedStyle`/`getBoundingClientRect` filtering, since the DOM's first `.row .card` is often off-screen/hidden after scrolling → click it → screenshot inspect state → click resume → screenshot closed state) rather than eyeballing a single static screenshot, per [[feedback_hard_debug_protocol]].

## Upgrade pass (v3) — real 3D floor + light/white room theme
Requested as a further follow-up: "add floor, make the room white." Two changes, three bugs found doing them — all three are general CSS lessons worth remembering beyond this file.

**What changed:** swapped `--bg`/`--ink`/`--mute` to a light palette (cards stay dark for contrast, like product tiles in a bright showroom); added an actual `.floorplane` element — a large flat rectangle anchored at the cards' vertical bottom edge (`top: calc(50% + 140px)`) with `transform-origin: top center; transform: rotateX(90deg)`, textured with `repeating-linear-gradient` grid lines, that recedes away in Z under the stage's single perspective context — plus its `background-position` is offset by `depth` each frame so the grid appears to scroll as you walk, instead of sitting static while cards move past it.

### Three real rendering bugs hit, all fixed
1. **A `radial-gradient` "spot fog" covered the entire viewport, not just the small area it was centered on.** A `radial-gradient(24% 14% at 50% 20%, transparent 60%, rgba(...) 100%)` was meant to be a small fog patch near the horizon. It isn't — **a CSS radial-gradient always paints its last color stop out to fill the *entire* rest of the gradient box**, not just inside the defined ellipse. So "transparent inside 60% of a small ellipse, bg-color from 60–100%" actually meant "bg-color solid everywhere outside that small ellipse," washing the whole scene. Fix: don't reach for `radial-gradient` to make a *small, bounded* patch of fog/glow on a full-size layer — either keep the radial genuinely full-bleed (accept it fills everything) or use a separate, explicitly small-sized/positioned element instead. Diagnosed by toggling `.refl`/`.glow`/`.fog` off one at a time via `page.evaluate` and re-screenshotting each combination — much faster than reasoning about gradient math from a screenshot alone.
2. **Cards passing very close to camera (`translateZ` approaching the stage's `perspective` value) rendered visibly desaturated/washed**, a real Chromium 3D-transform rendering artifact, not a CSS logic bug — confirmed by reading `getComputedStyle` (`opacity: 1`, correct dark `background-color`) while the actual painted pixels were pale grey. This was previously *masked* by an old symmetric opacity-fade formula that happened to fade near-camera items toward invisible anyway; a fix in the v2 upgrade (making near-camera items stay fully opaque, see above) inadvertently un-masked it. Fixed by clamping the transform's actual `translateZ` to a safe margin below the perspective value (`Math.min(z, 380)` against a `perspective:700px` stage) while still using the true `z` for scale/fade math — i.e. let it *look* close without letting the transform *literally* approach the clipping plane.
3. **`z-index: 999` on the inspected card did nothing against the inspect-mode backdrop.** `.row` has its own `transform`, which creates a new stacking context — so a row's `z-index:999` is only ordered relative to its *sibling rows*, not to elements outside `.track` (like the backdrop `div`, which had `z-index:8`). `.track` itself had no explicit `z-index`, so it defaulted to stacking-order `auto`/0 as a whole, and the backdrop painted over the entire track regardless of what z-index a descendant claimed. **z-index only ever competes within the nearest shared stacking context** — a high z-index buried inside a transformed/positioned descendant does not "win" against a sibling of its ancestor. Fixed by giving `.track` its own explicit `z-index:5` (above the backdrop's now-lowered `z-index:2`) rather than trying to out-rank the backdrop from inside a descendant.

All three were caught by isolating and directly testing (toggling layers, reading computed styles, comparing before/after screenshots at the same interaction point) rather than trusting how the CSS *read* on paper — same [[feedback_hard_debug_protocol]] method as the v2 pass.
